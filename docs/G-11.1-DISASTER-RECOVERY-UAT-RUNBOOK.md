# G-11.1 — Backup, Restore & Disaster Recovery UAT

## Objective
Prove a recoverable staging database and object-storage snapshot, measure achieved RPO/RTO, validate restored data and application connectivity, and retain provider-generated evidence. This is the next register item (formerly G-12), labelled G-11.1 at the operator's request.

## Critical boundary
The existing application continuity tables and JSON operational export are records/evidence only. They are not managed database backups and do not prove PITR. Never run `supabase db reset --linked`, destructive restore, bucket deletion, or failover against production. Do not copy production customer data into an unapproved test environment. Use an isolated recovery project and synthetic data.

## Required drill
1. Record the exact tested commit SHA, staging project ref, approved RTO/RPO targets, drill owner and change approval.
2. Capture the Supabase provider backup/PITR point identifier and completion timestamp from the provider dashboard/API. Preserve the original provider evidence.
3. Restore to a separate isolated recovery project, not over the source project. Record restore start/completion timestamps and destination ref.
4. Validate database integrity: expected schema/migration version, row-count checks for synthetic fixtures, key FK/constraint checks, auth-independent application reads, and no unexpected missing rows.
5. Validate object storage separately: bucket inventory, object manifest, object count/size/hash checks and successful retrieval of representative synthetic files. A database restore alone does not restore object bytes.
6. Verify required Edge Function configuration and secrets are present in the recovery environment without exporting or recording secret values. Verify DNS/domain cutover plan without changing production DNS.
7. Calculate measured RTO from restore initiation to validated service readiness. Calculate RPO from the last recoverable committed synthetic marker to the declared incident time. Compare against approved targets.
8. Capture logs, provider job IDs, screenshots or exported provider reports. Hash the evidence bundle. Record gaps and corrective actions; a failed drill is still a valid recorded outcome, not a pass.
9. Independently review the evidence and clean up the isolated recovery project only after approval.

## Application control-plane preflight
Run `npm run verify:g111-disaster-recovery`. In an authenticated staging SQL session, run `supabase/tests/g111_disaster_recovery_readiness.sql` (read-only transaction, rollback). This verifies the application-owned continuity plan tables and RPC grants only; it does not execute a backup or restore.

### Actual restore sequence

1. In Supabase Dashboard, select the source staging project and locate the provider-managed
   backup/PITR recovery point. Record the provider's backup identifier, completion time and
   retention/restore-point details. Preserve the original provider-generated confirmation.
2. Create or select a separate, empty recovery project in the approved region and plan.
   Confirm its project ref is not the canonical production ref
   `cvjmfplhdlfvqnnmzqcp` and not the source staging ref.
3. Initiate the provider-supported restore into that separate recovery project. Record the
   exact UTC start time and provider job/reference. Do not improvise a SQL dump/restore and
   call it PITR; it is a different recovery method and must be labelled accurately.
4. Record provider restore completion UTC. Then run database validation against the recovery
   project: expected migration/schema state, synthetic fixture counts, key FK/constraint
   checks, required extensions, and critical read paths. Preserve redacted output.
5. Independently restore object storage from its own approved backup/manifest. Verify bucket
   inventory, object count, byte size, SHA-256 for each test object and successful retrieval.
   Do not infer that database PITR restored object bytes.
6. Verify Auth configuration, Edge Function versions/configuration and required secret
   *presence* in the recovery environment. Never export or record secret values.
7. Run the critical synthetic workflows and confirm service readiness. Record the end time
   only after database, storage and application checks pass.
8. Calculate `measured_rto_minutes = validated_ready_utc - restore_started_at_utc`.
   Calculate RPO using the latest recoverable committed synthetic marker relative to the
   declared incident time; record both timestamps and the calculation basis.
9. Compare measured RTO/RPO to the targets approved before the drill. Record PASS or FAIL;
   never alter targets after seeing the result.
10. Have an independent reviewer inspect original provider evidence and sign the report.
    Retain failed evidence and corrective actions. Clean up the isolated recovery project
    only after owner approval.

### Supabase CLI safety

The linked read-only validation scripts in this repository may be used only after reviewing
their safeguards and setting the documented read opt-in. `supabase migration list --linked`,
`supabase db push --dry-run --linked`, and `supabase db lint --linked` are inspection/preflight
steps, not a managed PITR restore. Never run `supabase db reset --linked`. Do not run
`supabase db push --linked` or any destructive restore without a separate written approval.

### Evidence required to close G-11.1

The existing `scripts/run-g111-disaster-recovery-uat.mjs` validates evidence structure and
target thresholds. It does not connect to Supabase, restore database/storage, or independently
authenticate provider evidence. Closure requires original provider job records, database and
storage validation artifacts, measured timestamps, a tested commit SHA, target comparison,
and an independent signed review.
